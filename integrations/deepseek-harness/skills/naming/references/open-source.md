# 开源项目命名（package / registry / CLI 三面）

> 用途：product 模式在 **OSS / 开发者工具**场景的专用分支。读它的时机是第 2 步（定类型）与第 5–7 步（生成 → 可用性门）。
> 与消费品牌的分水岭：OSS 名字的第一验收场不是广告牌，而是 `import`、装包命令、`$ cmd` 三个地方——名字要同时过三关，任何一关要用户查文档才能对上，都是长期成本。
> 强度：**实证**＝注册表官方规则或已发表研究；**机构**＝官方规范；**经验**＝实践者共识；**法理**＝法规/判例；**判断**＝本文推断；**未验证**＝无一手来源。

## 1. 包名硬约束（按注册表，官方规则）

| 注册表 | 硬规则 | 后果 |
|---|---|---|
| **npm** | 新包名不得含大写字母；≤214 字符（含 scope）；必须 URL-safe；只有 scoped 包才允许以 `.`/`_` 开头 | 大小写不是风格问题，是发布失败 |
| **npm** | 官方建议：不与 Node 核心模块同名；不把 `js`/`node` 塞进名字；"会作为 `require()` 的参数，所以应简短但合理描述" | `-js`/`node-` 前后缀是纯噪音 |
| **PyPI** | PEP 503 归一化：小写 + 把 `-` `_` `.` 的连续段统一成单个 `-` | **`foo-bar` / `foo_bar` / `foo.bar` 是同一个名字** |
| **crates.io** | 仅 ASCII 字母数字与 `-` `_`；首字符须字母；≤64；大小写不敏感且**禁止只差 `-`/`_`** | 同上，分隔符不是自由度 |
| **RubyGems** | 多词用下划线；**扩展另一个 gem 用连字符**（`net-http-digest_auth` 给 `net/http` 加功能）；禁用大写 | 分隔符在这里**有语义**，不是审美 |
| **GitHub** | repo 名宽松；handle/org 全局唯一且不可重名 | 见 §4 |

- 出处：npm <https://docs.npmjs.com/cli/v10/configuring-npm/package-json>、<https://docs.npmjs.com/cli/v10/using-npm/scope>；PyPI <https://peps.python.org/pep-0503/>；RubyGems <https://guides.rubygems.org/name-your-gem/>（以上**机构**）。crates.io 的 `name` 字段规则见 <https://doc.rust-lang.org/cargo/reference/manifest.html>（**机构**），"首字符须字母 / 大小写不敏感 / 禁止只差 `-`\`_`"属**注册表层限制**，来自 Cargo 文档对注册表限制的说明 <https://github.com/rust-lang/cargo/commit/a4c1c6fa2abe81f5b868ea8c0032858f46ef2d46>（机构文档，**二手引用**，以 crates.io 现行报错为准）。
- **判据**：PyPI 与 crates.io 会把分隔符归一，所以"分隔符唯一"不是风格偏好而是**身份问题**——一个项目里不要同时出现 `foo-bar` 与 `foo_bar`。
- 落地：定名时选**一种**分隔符并在全家族贯彻；跨语言多包（JS + Python + Rust）优先选在三个注册表都**不需要变形**的写法。

## 2. bin 名与包名：一致，或可解释

- npm 的 `bin` 与 `name` 相互独立：单命令可写成字符串 `"bin": "cli.js"`（等价于用包名当命令名），多命令给对象（**机构**，同上 package.json 文档）。
- 两种可接受关系：① **同名**（`pkg` → `$ pkg`，记一次就够，优先选它）；② **短别名**（包名长，尤其 `@scope/very-long-name` 时给更短的 bin，且 `$ pkg` 能解析到同一入口）。
- 不可接受：bin 与包名毫无词源关系（用户永远记不住敲哪个）；多个包抢同一个 bin 名（PATH 冲突，装上谁算谁）。
- 落地：`@scope/` 已吃掉 6–10 个字符的记忆预算，**scope 越长，package 段越要短**；bin 名不重复 scope。

## 3. 注册表冲突与 squatting

- **先到先得是默认规则**：crates.io 明示 first-come first-serve，同时把"长期只占名、没有真实功能"列为违规，并禁止买卖包名（**机构**，<https://crates.io/policies>）。
- **PyPI 有申诉通道但很窄**：PEP 541 要求"弃用"同时满足「联系不上 owner + 12 个月无发布 + 主页无活动」；活跃项目的同名争议，维护者**不仲裁**（**机构**，<https://peps.python.org/pep-0541/>）。
- **scoped package 是最便宜的解法**：scope 归属个人/组织，只有你能往里发包，"不用担心别人先占了你的包名"（**机构**，npm scope 文档）。
- 决策顺序（**判断**）：① 查目标注册表是否被占 → ② 被占且是活跃项目：**改名，不要赌申诉** → ③ 属自己组织：用 scope 收编 → ④ 唯一可用名太丑时，接受 scope 而不是接受拼写畸形（`pkg-rs`、`pkg2`、`pkg-official` 全是反面）。
- 落地：把"已被占"当**预算约束**而非否决项——加 scope 的代价是每次 import 多打几个字符，改名的代价是社区找不到你，前者小得多。

## 4. org 与 repo：品牌层与产品层

- **org/handle = 品牌层**：全局唯一、不可复制，是真正稀缺的资产；**repo = 产品层**：允许大写与长描述，改名成本低。
- **经验**：org 当品牌、repo 当产品是最省事的默认。反例是拿 org 去占某个具体产品的名字——第二个产品出生时无家可归。
- 落地：如果未来会有第二个产品，第 1 步简报里就把 org 名一起定下（"org 是永久资产，repo 可随产品调整"）。

## 5. 可搜索 vs 可归类（OSS 独有的取舍）

- **通用词会被同题材内容淹没**：HN 上一手反例——项目叫 `plugin-update-checker`，搜文档会被一堆同类词埋掉；反过来，独特词更好搜但更难猜到用途（**经验**，<https://news.ycombinator.com/item?id=46237390>）。
- 所以不是"描述 vs 生造"二选一，而是**两段式**：① **可归类段**说明"我属于哪类东西"（`react-`、`-cli`、`-parser`、`db`）；② **独特段**用不与他人共享的词根让搜索落到你身上。
- 示例结构（自造）：`quarry-parser`（独特 + 归类）优于 `json-parser`（纯类别词，注定被埋），也优于 `Quarryx`（无归类，只能靠 README 解释）。
- 落地：生成阶段强制每个候选标注「归类段 / 独特段」，只占一段或两段都空的，进不了第 6 步。

## 6. 会议提问测试（conference talk test）

- 真实采用路径常是一句话：**"那个做 ___ 的 ___ 库叫什么？"** 请一个没听过项目的人向第三人转述，看第三人能否**一次搜索就找到**。
- 三种失败：① 通用词 → 搜出一屏同类；② 生造词 → 能搜中但转述者记不住；③ 要加限定词才搜得到（"那个 rust 的，不是 js 的"）→ 归类段缺失。
- 落地：把这句话写进第 9 步每个 finalist 旁，当**可用性证据**，不是修辞。

## 7. 与类型选型的接口

- OSS 的默认落点是 **associative（词根有指向）或短 descriptive**，不是纯 neologistic——纯生造在开发者场景的代价是"每次靠 README 解释这是什么"。四象限定义见 `name-types.md` §2、§4.1，本文只补"三个调用面"与"注册表硬约束"这两层。
- 落地：第 2 步的类型声明加一行 `registry_targets: npm | pypi | crates | rubygems | github`——不同注册表的硬规则会直接淘汰候选（§1）。

## 8. OSS 命名检查表（打勾用）

- [ ] 全小写，无大写字母（防发布失败）
- [ ] 全家族只用一种分隔符，且已确认它在 PyPI/crates 归一后不易与他包混同
- [ ] 与目标语言标准库/核心模块不同名
- [ ] 未使用 `-js` / `node-` / `-py` / `-rs` 之类冗余语言后缀
- [ ] `npm i ___`、`pip install ___`、`cargo add ___` 各念一遍都顺
- [ ] bin 与包名同名，或有一个**可解释**的短别名，且无跨包 bin 抢名
- [ ] 目标注册表已查（API 404 = 可用）；被占时已决定用 scope 而非畸形变体
- [ ] org/handle 与产品名分开考虑，org 名能容纳第二个产品
- [ ] 名字含一个"可归类段"和一个"独特段"
- [ ] 会议提问句能一次搜索命中
- [ ] 拼写不会被听写成另一个已存在的包（听写测试，见 `availability.md` §5）
- [ ] brief 里写了 `registry_targets`，候选已按各注册表规则筛过
