# 产品命名 Playbook（product 模式，9 步）

## 第 1 步 · 命名简报（不建简报不生成）
问清：① 做什么（一句话）② 给谁 ③ 什么调性（技术/温暖/俏皮/权威）④ 是否品牌家族（有则记 `architecture`，见 `brand-architecture.md`）⑤ 禁用词/概念/风格 ⑥ 目标平台（域名 / npm / GitHub / 应用商店 / 社媒 / TM；OSS 另记 `registry_targets`，见 `open-source.md`）⑦ **必含词 / 必避词 / 风格区**（生成时的硬约束，比事后过滤更有效）⑧ 语言与地区（中文场景 → `zh-phonetics.md`）。→ 模板见 `templates/naming-brief.md`。用户已贴简报则直接用。

**为什么要把"必避词"前置**：命名是合取型决策，事后过滤只会让 50 个候选里 45 个白生成；把 `must_avoid`（如 `-ly/-ify/-ora`、`AI`、`Cloud`、"Solutions"）写进约束，从源头压掉 AI 味。（依据见 `sources.md` §1；配额阈值见 `ai-era.md` §1）

## 第 2 步 · 定名字类型（别跳过）
在生成之前先声明这一轮要哪种类型，因为它决定后面所有取舍：

- 用 **`name-types.md`** 的 2×2（真实词 × 相关性）选一个主类型：`descriptive` / `deviant` / `associative` / `neologistic`；
- 按场景定目标函数：消费品牌 → 记忆与商标优先；B2B SaaS → 可信 + 可解释（可配副名）；开发者工具/OSS → 可猜可搜可 import；**内部系统 → 自描述优先**（与 GDS 规范一致，见 `name-types.md` §4.2）；
- 输出一行 `name_type / audience / protect_priority`，写进简报。选型错了＝后面每一步都在补偿。

## 第 3 步 · 竞品命名占位图（结构判断，替代"只查重"）
**不要只查重，先看"位置"**：列 8–12 个竞品名 → 每个打类型标签（Functional / Invented / Experiential / Evocative）与投入强度（低/中/高）→ 输出两句话：

- **已被占满的语义区**：哪些意象、词根、音节已经被反复使用（例如所有监控产品都在用"守卫/眼睛"）；
- **2–3 个空白位**：下一轮 30–50 个候选必须**声明自己属于哪个空白位**，不属于的回炉。

作用：把"撞名"从个案判断变成结构判断；也让第 8 步的"差异化"分有依据，而不是凭感觉。
（方法来源：Igor International 的 Competitive Analysis 与四类命名法，见 `sources.md` §1。）

## 第 4 步 · 隐喻探索（先想"什么和它像"）
**6 个找隐喻的问题**（对"简化核心功能"逐条问）：
1. 它在物理世界像什么工具/角色？（哨兵、码头工人、保险库）
2. 它对用户是哪种关系？（向导、教练、守门人、副驾）
3. 它的核心动作像什么自然过程？（涌流、生长、点燃、净化）
4. 它解决的是哪种"痛"？痛的反面是什么意象？
5. 它在神话/历史/科学里对应哪个原型？
6. 有没有一个外语词恰好精确表达（kaizen/hygge/saudade）？

**起步 territory 地图**：守卫/看护、容器/仓储、路径/导航、工具/工艺、自然/元素、生物/生态、音乐/节奏、建筑/结构、神话/占星、拟人角色、外来语根（拉丁/希腊/日/意）。
选 2–3 个 territory。简报明确时可自主选，不必让用户选；简报模糊或方向等价时才让用户挑。

> 深度版（可选，非本包文件）：上游 `glacierphonk/naming` 仓库里的 metaphor-mapping 文档为 11 个产品题材各给了一张 territory 地图（监控、后台进程、数据处理、通信、安全、性能、创作工具、项目管理、金融、教育、健康），本包未内置，需要时按题材现场展开即可。

## 第 5 步 · 生成候选（内部，30–50 个，不展示）
方法：territory 单词 / 双词复合 / 变形（截断、混拼、加后缀）/ 相关外语词 / 先声音后意义（念音节找顺口的组合）。保留不完美的，能看出模式。
**约束**：不得违反第 1 步的 `must_avoid`；每个候选记一行"类型 + 空白位"。

## 第 6 步 · 过滤（内部，砍到 ~10）
顺序：**先过否决门**（`evaluation.md` A1 + `anti-patterns.md`），**再**单轴按差异化粗排。命中 ≥1 条否决项即淘汰；命中 ≥2 个红旗即淘汰。

## 第 7 步 · 可用性硬核验（blocking，必做）
输出固定的可用性行（`availability.md` 「可用性门」）：**L1 公开冲突**（先做，最常杀名）→ 域名/包名/社媒 → **L2 商标库同名** → **L3 律师 clearance（不做，只建议）**；**L1.5 生成式可提及性**只在"买家会问 AI 助手"时插入（见 `ai-era.md` §4），跑了才写，没跑不写。
- 顺序：先竞品冲突搜索（"[name] [品类]" 有直接竞品＝死，立即弃）→ 再域名/包名/社媒。→ 见 `availability.md` + `scripts/check-availability.sh`。
- 字典常见单词跳过 .com/.dev/.io 精确匹配（基本被占），直接看 get[name]/use[name] 变体与 .sh/.site。
- **域名缺失不是否决项**：给替代路径（`getX`/国别域/路径式落地）即可；别为了 .com 换掉一个更好的名字。
- 六个现实测试（`availability.md` §5）：嘈杂通话、iOS/Android 听写、私密窗口搜索、10 平台 handle、**AI 朗读门**（模型能否不加改写地复述名字）、**品类默认探测**（不带上下文问"X 是做什么的"，看默认品类标签是否跑偏，见 `ai-era.md` §5）。
- 存活 <3 个 → 回第 5 步加量，**不降标准**。

## 第 8 步 · 评分（内部）
先过否决门，再按 `evaluation.md` A3 的 6 维 0–3 锚点打分（权重按场景可改），跑 A4 语境句子测试；必要时用 A7 的 Igor 9 维交叉校验。语音学习只在同分候选间做决胜（`phonosemantics.md`）。

## 第 9 步 · 呈现（第一次给用户）
3–5 个 finalist，每个：名字 / **类型与让步**（"它是 arbitrary 型，所以我们放弃了'一眼看懂'"）/ 起源故事（15 秒）/ 为何成立（满足哪些原则）/ 可用性状态（L1 / L1.5 / L2 / L3，见 `availability.md`）/ 风险 / **descriptor（品类词）+ tagline**（并标 `optimize: liking | memory`，见 `taglines.md`）。跨语言场景加一行"本地名策略"（见 `localization.md`）。建议用户 24h 后再定。

## 三个硬测试
- **电话测试**：说一次 → 对方能复述、能拼对、24h 还记得。需逐字母拼＝坏。
- **15 秒故事**：讲不出"为什么叫这个"＝回去重做隐喻。
- **缩短测试**：若必然被缩写，缩写是否还好看（Kubernetes→K8s 可以）。

## 长度（产品侧：**偏好权重，不是阈值**）
- 经验偏好：1–2 音节、短词更容易被口播与记住——但这是**启发式**，不是阈值，**不得用于否决**。
- **重要更正**：2026 年一项直接研究（Zee, Willems, Brengman & Desmet, *Journal of Brand Management*）发现名字长度对"态度"与"再认"的影响方向不同，**更长的名字在再认上反而可能更强**；"4–6 个字符是甜区"**没有任何一手来源**，本技能已删除该说法。
- 落地：把长度当**权重**（在 `evaluation.md` 的"记忆/听感"维度里体现），不当硬门；跨语言必须重校准——中文以「字」计数、还要算声调与谐音，见 `zh-phonetics.md` §1–§3；**不要套英文字符数**。
