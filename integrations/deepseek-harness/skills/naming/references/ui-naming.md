# UI 层命名：界面文案 / 组件 / CSS / 无障碍 / i18n

> 用途：code 模式，命名对象是**用户看得见或听得见**的东西——按钮、菜单、空状态、错误提示、CSS 类名、组件名、路由、aria 标签、i18n key。
> 为什么单列：语言层的规则（camel/snake、S-I-D）能管代码标识符，但**管不了"按钮上写什么字"**。UI 名字错了，用户不会报 bug，只会点错。
> 强度：**机构**＝官方规范；**经验**＝设计系统共识；**判断**＝本文推断。

## 1. 按钮与操作：动词优先，且**说结果**

| 规则 | 好 | 坏 | 理由 |
|---|---|---|---|
| 用**具体动词**开头，不用"确定/提交" | `保存更改`、`发布`、`删除 3 个文件` | `确定`、`提交`、`执行` | 用户要能预测点了会发生什么 |
| **危险操作写清后果与范围** | `永久删除 3 个文件` | `删除` | 不可逆操作必须自解释（**机构**：这是主流设计系统共识） |
| 同一动作**全站一个词** | 全站只用 `删除` | `删除`/`移除`/`清理` 混用 | 一个概念一个词（与 `code-style.md` §10 同源） |
| 按钮文案**不用"是/否"** | `放弃更改` / `继续编辑` | `是` / `否` | 对话框里的"是"指代不明 |
| 一个页面**只有一个主按钮** | 主：`发布`；次：`存草稿` | 三个同权重按钮 | 层级靠视觉，也靠命名 |

## 2. 状态与空态：说"现在怎样 + 下一步能做什么"

- **空状态**：`还没有项目` + 主操作 `新建项目`。禁止只写 `暂无数据`（用户不知道"数据"指什么）。
- **加载**：`正在加载项目…`；**完成**：`已保存`（不写 `操作成功`）。
- **错误**：**说清对象 + 原因 + 出路** —— `无法保存：文件名包含 / 字符。改名后重试。` 禁止 `出错了`、`系统异常`。
- **权限不足**：`你没有编辑此项目的权限。请联系管理员。`（不只写 `403`）。
- 判据：把这条文案单独贴给一个没用过产品的人，他能说出"发生了什么、我该做什么"吗？

## 3. CSS 类名与设计令牌

| 层 | 约定 | 例 |
|---|---|---|
| 组件类 | BEM：`block__element--modifier`（或项目既有方案） | `card__title--muted` |
| 状态类 | `is-` / `has-` 前缀 | `is-open`、`has-error` |
| 工具类 | 单一职责，名字即效果 | `u-mt-4`、`text-center` |
| 设计令牌 | **语义名，不是外观名** | `--color-danger` 而非 `--color-red` |

- **语义令牌 > 外观令牌**（**经验**）：`--color-danger` 换主题时不用改全部引用；`--color-red` 在深色模式下会说谎。
- **别用位置/顺序命名**：`left-panel`、`third-column` 会随布局腐烂；用职责：`filter-panel`。

## 4. 组件与路由命名

- **组件名 = 名词**（`OrderSummary`、`PaymentForm`），**不带** `Component`/`Widget` 后缀（与 `code-style.md` §9 的 weasel 后缀一致）。
- **路由用名词复数、小写连字符**：`/orders`、`/orders/:orderId/items`；动词交给方法（`POST /orders`），不要 `POST /createOrder`（**机构**：REST 惯例，见 `api-naming.md` §1）。
- **URL 与页面标题同源**：`/orders` ↔ `订单` ↔ `<title>订单</title>`，三者不一致会让面包屑与搜索都错位。

## 5. 无障碍（aria / alt / label）

- **`aria-label` 说动作与对象**：`aria-label="删除订单 #1024"`，不是 `aria-label="删除"`（屏幕阅读器里十个"删除"无法区分）。
- **图标按钮必须有可读名**：只有图标的按钮没有 `aria-label` = 对读屏用户不存在。
- **`alt` 分两类**：内容图说内容；装饰图 `alt=""`（**机构**：WCAG 要求，宁可空也不要重复周围文字）。
- **表单 label 与输入同词**：`<label>邮箱</label>` + `placeholder="you@example.com"`，不要让 placeholder 充当 label（它一输入就消失）。

## 6. i18n key 命名

- **key 表达语义，不表达文案**：`orders.empty.title` ✅；`noDataText` ❌（改文案时 key 就撒谎）。
- **层级 = 页面/组件 + 元素 + 角色**：`checkout.payment.submitButton`。
- **不要在 key 里写复数/性别**：交给 ICU 复数规则；`item.one` / `item.other` 由消息格式处理。
- **禁止在 key 里塞中文或空格**：会破坏工具链与 grep。

## 6.5 机器检查（能测的那一半）

```
python scripts/check-ui-names.py <path...> [--scan aria|i18n|copy|css|all] [--strict]
```

覆盖 8 条可判定规则：`generic_button`（「确定/提交/OK」）、`danger_no_scope`（危险操作没写范围）、
`aria_generic` / `icon_no_label`（无对象或空的 aria-label）、`token_appearance`（`--color-red` 这类外观令牌）、
`i18n_key_text`（含中文/空格或值式命名的 key）、`vague_error`（「出错了」）、`empty_state`（「暂无数据」）。

**边界**：它只能抓"是否可被理解"的形式部分；语气、人称（你/您）、句首大写由产品的 content style guide 定，
不在本技能范围内（见 §8）。自检：`python scripts/test_check_ui_names.py`（11 用例，含大量"合规写法不该被误报"）。

## 7. UI 命名自检（8 项）

- [ ] 每个按钮都是"动词 + 对象"，危险操作写清范围与不可逆
- [ ] 同一动作全站一个词（无 删除/移除/清理 混用）
- [ ] 空态/错误态都说清"发生了什么 + 我该做什么"
- [ ] CSS 类遵循项目既有方案（BEM 或 utility），状态类用 `is-/has-`
- [ ] 设计令牌是语义名（`--color-danger`），不是外观名
- [ ] 组件名是名词、无 `Component/Widget` 后缀
- [ ] 每个图标按钮有可读的 `aria-label`，且含对象
- [ ] i18n key 是语义路径，不含文案/中文/空格

## 8. 边界（本技能不做的事）

- **不做 UI 文案风格指南**：语气、大小写（Sentence case vs Title Case）、人称（你/您）由产品自己的 content style guide 定；本文件只给"能否被理解"的判据。
- **不做视觉层级**：按钮主次靠设计系统，不靠命名。
- **不覆盖设计令牌体系**：只给命名原则，具体令牌表由使用方维护。
