# 代码组织：突出核心算法与规范（主流程在前，样板/工具后置）

> **目的**：代码一多，核心算法与规则最容易被样板、边界、工具代码淹没。本规则要求**把核心算法与规范提炼到最显眼处**、非核心代码下沉收起，做到"**一眼看到算法、一屏读完规则**"。
> **行为指令**：写/改任何含判断·校验·算法的非平凡方法时按此排布，让读者**不看细节代码也能先理解算法与规范**。

## 规范（Must）

1. **先规范、后实现**：核心类/方法开头，用 `① ② ③ …` 编号步骤（或等价的简短伪代码/注释块）把"算法 / 规则 / 规范"讲清楚。**这些注释应能脱离代码独立阅读**（可直接搬进文档/交接说明）。
2. **主流程一条主干**：真正的算法写在唯一的"主流程方法"里，按编号步骤推进；主流程里只保留与算法直接相关的调用，不掺样板。
3. **非核心下沉**：样板代码（读写 IO、异常包装、参数解析、纯工具判断）移到主流程之后，或抽成 `private` 工具方法/独立类；**不得夹在主流程中间打断阅读**。
4. **类内固定顺序**：`常量/字段` → `对外公共入口` → **主流程** → 一条分隔线 → **全部工具方法**。
5. **规模红线**：核心算法与规范应能**在一屏（约 60~80 行）内读完**；超出就拆文件/提取子算法（并保留一层概述注释），不要继续往一个方法里堆。

## 为什么

- 代码≈实现细节，规范≈稳定的意图。先规范后代码，评审/交接**只看算法与规则**即可判断对错。
- 样板与工具下沉，主流程才"看得清"；否则代码越多，核心越被淹没。

## 反例（不要这样做）

- 把一条校验/算法拆成 5~6 个互相调用的小方法，主流程只剩一串函数名 → **算法消失**，读者必须跳读才能拼出规则。
- 工具/样板代码插在主流程之间，把算法切碎。
- 只有实现没有"规则注释"，读者只能从代码反推意图。
- 一个方法几百行，样板与核心混在一起，看不出主干。

## 正例（本次 SSRF 校验的落地样式）

```
// ===== 主流程（算法 / 校验规则）—— 看这一个方法即可 =====
public static URL validate(String rawUrl) {
    // ① 空值直接拒
    // ② 解析成 URL 结构
    // ③ 只允许 http/https/ftp
    // ④ 取 @ 之后的真实 host 与端口
    // ⑤ 主机白名单精确命中（→ matchesAllowList）
    // ⑥ 解析 IP：环回/链路本地一律拒（→ isAlwaysBlocked）；未配白名单再禁私网（→ isPrivateOrReserved）
    // ⑦ 产出 java.net.URL
}
// ===== 工具方法（仅供主流程调用）—— 零件，按需查 =====
/** 统一的拒绝出口 */ ...
```

## 检查清单

- [ ] 核心算法/规范有编号步骤（或伪代码）注释，且**可脱离代码独立阅读**
- [ ] 主流程是类里第一个业务方法，**核心算法在一屏内可读完**
- [ ] 样板/工具全部后置，不打断主流程
- [ ] 只读"主流程 + 注释"即可讲清规则，无需先读工具方法

> 适用：校验器、解析器、状态机、结算/算法类，以及任何"步骤清晰但样板/工具多"的方法；简单 CRUD 不强制。
